===============================
Product Requirements Document
Component: collabops-git-executor
===============================

📌 Purpose
----------
The `collabops-git-executor` is a backend component in the CollabOps platform responsible for executing actual Git operations. It interacts with `collabops-git-http` and `collabops-git-ssh` gateways to perform commands like `clone`, `fetch`, `push`, and returns either structured JSON responses or Git-specific packfile streams.

🧱 Architecture
--------------
Git Client (SSH/HTTP)
    ↓
Gateway Layer: collabops-git-ssh / collabops-git-http
    ↓ (REST / RPC)
collabops-git-executor
    ↓ (go-git)
Filesystem (e.g., /var/lib/git/repos/{user}/{repo}.git)

**Additional Direct Communication:**
Orchestrator (FastAPI) → collabops-git-executor (REST API for high-level Git operations)

🔧 **OFFICIAL ARCHITECTURE CLARIFICATION** (Architecture Team)
==============================================================

**1. collabops-git-http (HTTP Gateway)**
---------------------------------------
Responsibilities:
- Accept Git Smart HTTP requests over HTTP (e.g. clone, push)
- Route requests to collabops-git-executor
- Extract and optionally decode JWT (Authorization: Bearer <JWT>)
- Forward headers like X-USER-ID to executor
- Stateless gateway layer
- Does NOT handle Git logic or touch .git files

Supported Endpoints:
- GET /info/refs?service=git-upload-pack
- POST /git-upload-pack  
- POST /git-receive-pack

**2. collabops-git-executor (Git Logic Worker)**
----------------------------------------------
Responsibilities:
- Core Git logic using go-git
- Handles Smart HTTP protocol implementation:
  - git-upload-pack (clone/fetch)
  - git-receive-pack (push)
- Decode JWT (if gateway does not)
- Check permissions via API metadata service
- Read/write Git objects from/to bare .git repos
- Stream valid Git responses to client

Smart HTTP Behaviors:
- Ref negotiation
- Capability declaration
- Packfile parsing
- Reference updates

JWT Handling:
- Typically decoded here using K8s Secret (public key)
- If decoded in gateway, only X-USER-ID passed here
- Responsible for validating access and acting as Git worker

**Smart HTTP Flow Examples:**

Git Clone Flow:
1. Client: GET /info/refs?service=git-upload-pack → Gateway → Executor
2. Executor: Returns refs and capabilities
3. Client: POST /git-upload-pack → Gateway → Executor  
4. Executor: Streams packfile

Git Push Flow:
1. Client: POST /git-receive-pack → Gateway → Executor
2. Executor: Decodes JWT or uses X-USER-ID, validates permission, parses packfile, updates .git store

🔐 Authentication/Authorization
-------------------------------
* Core principle: JWT is validated once and user info is passed via header.

## Path A (Preferred Flow - via Orchestrator)
1. Client logs in → gets JWT from Orchestrator.
2. Web app calls Gateway (HTTP/SSH) with JWT.
3. Gateway forwards:
   - REST/RPC call to Executor
   - Includes `X-USER-ID` (parsed from JWT by Orchestrator)
4. Executor uses `X-USER-ID` to query API-Service (Metadata) for access.

→ `Executor` is dumb. It doesn't parse JWT.

## Path B (Fallback - Gateway Decodes JWT)
1. Client calls HTTP Gateway directly (e.g. `git clone` from CLI).
2. JWT sent in `Authorization: Bearer` header.
3. Gateway decodes JWT (using public key or shared secret).
4. Gateway passes `X-USER-ID` to Executor.

→ `Executor` still stays dumb.

❗Only in extreme cases (debugging, local CLI dev) should Executor decode JWT directly:
- Must mount `public.pem` via k8s Secret
- Not a recommended path

🎯 ONLY header passed = `X-USER-ID`. Other fields (e.g. `X-USER-SCOPE`, `X-USER-NAME`) are deprecated.

🔒 **ENDPOINT ACCESS CONTROL MATRIX**
=====================================

**CRITICAL**: Each component has specific endpoint access permissions. Unauthorized access must be rejected.

| Endpoint Pattern | HTTP Gateway | SSH Gateway | Orchestrator | Description |
|-----------------|--------------|-------------|--------------|-------------|
| **Git Smart HTTP Protocol** |
| GET /{owner}/{repo}/info/refs | ✅ | ❌ | ❌ | Git reference advertisement |
| POST /{owner}/{repo}/upload-pack | ✅ | ❌ | ❌ | Git fetch/clone operations |
| POST /{owner}/{repo}/receive-pack | ✅ | ❌ | ❌ | Git push operations |
| **Git SSH Protocol** |
| POST /ssh/upload-pack | ❌ | ✅ | ❌ | SSH fetch/clone operations |
| POST /ssh/receive-pack | ❌ | ✅ | ❌ | SSH push operations |
| **REST API Endpoints** |
| GET /repos/{owner}/{repo}/tree | ❌ | ❌ | ✅ | Browse repository tree |
| GET /repos/{owner}/{repo}/blob | ❌ | ❌ | ✅ | Get file content |

**Access Control Implementation:**
1. **Source Identification**: Use headers to identify the calling component:
   - `X-Source: http-gateway` - From HTTP Gateway
   - `X-Source: ssh-gateway` - From SSH Gateway  
   - `X-Source: orchestrator` - From Orchestrator
   
2. **Middleware Enforcement**: Implement middleware that:
   - Validates `X-Source` header presence
   - Checks endpoint access permissions based on the matrix
   - Returns `403 Forbidden` for unauthorized access attempts
   - Logs security violations for monitoring

3. **Authentication Headers**:
   - Gateways: Pass `X-USER-ID` (extracted from Git credentials/JWT)
   - Orchestrator: Pass `X-USER-ID` (from authenticated session)
   - All: Include `X-Request-ID` for tracing

4. **Security Considerations**:
   - Gateways should NEVER access REST API endpoints
   - Orchestrator should NEVER access Git protocol endpoints
   - Validate source IP addresses in production (Kubernetes network policies)
   - Rate limit by source to prevent abuse

**Example Middleware Pseudocode:**
```go
func SourceValidationMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        source := r.Header.Get("X-Source")
        endpoint := r.URL.Path
        
        if !isAuthorizedSource(source, endpoint) {
            logger.SecurityEvent("unauthorized_access", source, endpoint)
            http.Error(w, "Forbidden", http.StatusForbidden)
            return
        }
        
        next.ServeHTTP(w, r)
    })
}
```
