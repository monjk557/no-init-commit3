## 1. Go HTTP 프레임워크와 성능 최적화

### 정리내용

GopherCon에서는 net/http, gin, fiber, fasthttp 기반 프레임워크들의 특성과 트레이드오프에 대한 설명이 있었다.

- **net/http**: Go 표준 패키지로 가장 안정적이며, 대규모 트래픽 환경에서도 예측 가능성이 높다. 라우팅 기능은 포함되어 있지 않아 외부 패키지를 함께 사용하는 경우가 많다.

- **gin**: Tree 기반 라우터 알고리즘을 사용하며, 학습 곡선이 낮고 범용적으로 사용하기 좋은 프레임워크다. 대부분의 서비스에서는 성능과 개발 생산성의 균형이 잘 맞는다.

- **fiber**: fasthttp를 기반으로 하며, 메모리 재사용을 적극적으로 활용해 높은 성능을 목표로 한다. 다만 이로 인해 요청 스코프를 벗어난 데이터 사용 시 주의가 필요하다. 예를 들어 fiber.Ctx에서 반환된 문자열이나 바이트 슬라이스는 내부 버퍼를 재사용하므로, 고루틴 등에서 비동기적으로 사용할 경우 반드시 복사해야 한다. 이러한 특성은 공식 문서와 다수의 사례에서 반복적으로 경고되는 부분이며, 성능 최적화의 대가로 개발자가 메모리 라이프사이클을 명확히 이해해야 한다.

**결론**: 극단적인 성능이 필요한 경우 fiber나 fasthttp가 선택지가 될 수 있으나, 일반적인 서비스에서는 gin 또는 net/http가 더 안전한 선택이 된다.

### Reference

Go 커뮤니티와 Google 내부 서비스 사례를 보면, net/http는 여전히 가장 안정적인 기준점으로 사용된다. 실제로 Google, Kubernetes, Prometheus 계열 프로젝트들은 net/http를 기반으로 하고, 라우팅이나 미들웨어는 외부 패키지로 조합하는 방식을 취한다. 이는 성능보다는 예측 가능성과 디버깅 용이성을 우선시한 선택이다.

Gin은 내부적으로 httprouter 계열의 트리 기반 라우팅을 사용하며, 이 구조는 공식 문서에서도 성능의 근거로 언급된다. Fiber와 fasthttp는 더 높은 성능을 목표로 하나, 메모리 재사용 전략으로 인해 API 사용 시 라이프사이클을 명확히 이해해야 하며, 이 점은 공식 문서와 이슈에서도 반복적으로 강조된다.

### 팁: Fiber / fasthttp 사용 시 메모리 안전성

Fiber나 fasthttp에서는 요청 컨텍스트가 반환하는 string이나 byte slice가 내부 버퍼를 재사용한다. 따라서 요청 스코프를 벗어나 사용하는 경우 반드시 복사가 필요하다.

```go
func handler(c *fiber.Ctx) error {
	// bad: 내부 버퍼 참조를 그대로 넘김
	result := c.Params("foo")
	go func() { useString(result) }()

	// good: 명시적으로 복사
	buffer := make([]byte, len(result))
	copy(buffer, result)
	resultCopy := string(buffer)
	go func() { useString(resultCopy) }()
}
```

Unsafe.String이나 unsafe.SliceData를 활용해 zero-copy를 시도할 수 있으나, 이는 성능 최적화가 정말 필요한 구간에서만 제한적으로 사용해야 한다. 기본 원칙은 **"경계를 넘길 때 복사"**다.

## 2. Go의 최소 추상 철학과 함수형적 접근

### 노트 정리

Go는 함수형 언어가 아니며, 순수 함수와 부수 효과를 분리하는 실용적 접근만을 취한다.

Go의 핵심 철학은 불필요한 추상을 제거하고, 반드시 필요한 추상만 최소 크기로 유지하는 것이다. 이는 동시성, 객체 모델, 오류 처리 전반에 걸쳐 일관되게 나타난다.

- **동시성**: goroutine과 channel이라는 최소한의 도구만 제공
- **객체 지향**: struct, method, interface, embedding으로 제한
- **오류 처리**: 예외가 아닌 다중 반환값으로 명시적으로 표현

이러한 최소 추상은 생산성을 높이지만, 동시에 복잡한 동시성 로직에서는 테스트와 유지보수를 어렵게 만드는 단점도 존재한다.

### Reference

Go의 "최소 추상" 철학은 Rob Pike의 Go Proverbs와 Effective Go 전반에 걸쳐 일관되게 드러난다. 인터페이스, 동시성, 오류 처리 모두에서 공통적으로 "필요한 것만 제공하고, 나머지는 조합으로 해결한다"는 방향을 취한다.

Google 내부에서 context가 표준화된 것도 같은 맥락이다. 최소한의 API로 취소, 데드라인, 요청 스코프 데이터를 전달하되, 과도한 프레임워크를 만들지 않는 것이 목표였다. 이는 Go가 함수형 언어는 아니지만, 순수 함수와 부수 효과를 구분하려는 실용적 접근을 취한다는 점을 잘 보여준다.

### 팁: 순수 로직과 부수 효과 분리 기준

- 입력과 출력만으로 설명 가능한 로직은 순수 함수로 유지한다.
- 시간, I/O, 네트워크, 고루틴 생성은 "경계"로 밀어낸다.
- 테스트에서 순수 로직은 병렬(`t.Parallel`)로 돌릴 수 있어야 한다.

## 3. 최소 추상의 한계와 동시성 복잡성 문제

### 노트 정리

GopherCon 세션에서는 Go의 CSP 기반 동시성 모델이 실제 대규모 시스템에서 겪는 어려움도 함께 다뤄졌다.

goroutine과 channel이 복잡하게 얽힌 구조에서는 cancellation, graceful shutdown, 테스트 안정성 확보가 매우 어려워진다. non-deterministic select, 시간 의존 테스트, CI 환경에서의 flaky test 문제도 자주 발생한다.

이러한 문제는 Go 자체의 결함이라기보다는, 최소 추상을 그대로 노출한 상태에서 복잡한 도메인을 다루려 할 때 발생한다.

### Reference

대규모 Go 서비스 사례(Uber, Kubernetes 등)에서도 goroutine과 channel만으로 복잡한 수명 관리를 하는 것은 어렵다는 점이 반복적으로 보고된다. cancellation, graceful shutdown, 에러 전파를 모든 고루틴에 일관되게 적용하는 것은 생각보다 많은 보일러플레이트를 만든다.

이 때문에 errgroup, run.Group 같은 "준표준" 도구들이 등장했고, 이는 최소 추상을 유지하되 동시성의 생명주기를 구조화하려는 시도로 볼 수 있다. 즉, 문제는 Go의 동시성 모델이 아니라, 복잡한 도메인을 그대로 노출시키는 설계에 있다.

### TIP: 동시성 제어 기본 도구 선택 기준

- **단순 병렬 처리**: worker pool
- **상태 공유**: sync.Map (read-heavy일 때)
- **조건 기반 대기/신호**: sync.Cond (channel로 대체 불가할 때만)

```go
cond := sync.NewCond(&sync.Mutex{})
ready := false

go func() {
	cond.L.Lock()
	for !ready {
		cond.Wait()
	}
	cond.L.Unlock()
}()
```

sync.Cond는 강력하지만 디버깅이 어렵기 때문에, 공용 유틸이나 캡슐화된 구조 안에서만 사용하는 것이 좋다.

## 4. Effect 개념과 Effect Handler에 대한 소개

### 노트 정리

이러한 배경에서 제안된 것이 Effect 개념이다.

**Effect**란 입력과 출력만으로 표현할 수 없는 작업, 즉 I/O, 시간, 네트워크, 동시성 같은 부수 효과를 의미한다. 핵심 아이디어는 이러한 Effect를 즉시 실행하지 않고, 선언된 값 또는 작업으로 취급하여 실행 시점을 위임하는 것이다.

- **순수 함수**: 표로 표현 가능한 변환(tableizable)으로 간주하고, 핵심 데이터 변환 로직으로 유지
- **부수 효과**: Effect로 분리하여 격리

**Effect handler**는 이러한 Effect를 실제로 수행하는 주체로, 동시성 제어, 실행 순서, 자원 관리를 한 곳에서 담당한다.

이 접근은 goroutine과 wait group을 비즈니스 로직에서 제거하고, 도메인 로직이 본질적인 문제에만 집중하도록 돕는다. 다만 Effect를 과도하게 미루는 구조는 디버깅과 추적을 어렵게 만들 수 있으며, 이를 보완하기 위한 대안으로 대수적 효과 처리기 개념도 함께 언급되었다.

### Reference

Effect 개념은 함수형 언어에서 오래된 패턴이며, Go에서는 "동시성/부수 효과를 도메인 로직 밖으로 밀어내려는 시도"로 해석하는 것이 가장 안전하다. Effect handler는 새로운 패러다임이라기보다, context, errgroup, supervisor 패턴을 하나의 개념으로 묶은 설계에 가깝다.

다만 Go 커뮤니티에서 표준으로 합의된 패턴은 아니며, 복잡한 orchestration 레이어에서만 제한적으로 적용하는 것이 현실적이다. 도메인 로직 자체가 handler에 의존하게 되면, 오히려 추상이 새로운 복잡성을 만들 수 있다.

### TIP: Effect 패턴 적용 가이드라인

- 도메인 로직은 effect를 "선언"만 하고 실행하지 않는다.
- handler는 infra / runner / orchestration 레이어에만 둔다.
- effect가 중첩되기 시작하면 도입을 재검토한다.

## 5. Effect 패턴에 대한 기술적 검증 및 위치 정리

### 노트 정리

Effect 개념 자체는 오래된 패턴이며, 순수 함수와 부수 효과를 분리하려는 시도는 함수형 언어 전반에서 공통적으로 나타난다.

다만 Effect handler 패턴은 Go의 표준 패턴은 아니며, Uber나 Google의 공식 가이드에도 명시적으로 포함되어 있지는 않다.

따라서 이 패턴은 전사적인 기본 규칙이라기보다는, 동시성이나 오케스트레이션 복잡도가 높은 레이어에서 선택적으로 고려할 수 있는 실험적 접근으로 보는 것이 타당하다. 핵심 도메인 로직에는 적용을 제한하고, Runner, Task orchestration, infra 레이어에서만 신중히 도입하는 것이 안전하다.

### Reference

Go 공식 문서와 대형 OSS를 기준으로 보면, 동시성 문제의 1차 해법은 context 기반 취소 전파와 errgroup이다. Effect handler는 이 기준을 넘어서야 할 만큼 복잡한 경우에만 고려할 수 있는 실험적 도구다.

따라서 내부 코드 규칙에서는 Effect 패턴을 "표준"이 아닌 "선택적 실험"으로 분류하고, 적용 범위와 금지 영역을 명확히 하는 것이 중요하다.

### TIP: Effect 패턴 도입 전 체크리스트

- errgroup + context로 해결 가능한가?
- goroutine 수명과 종료 조건이 한눈에 보이는가?
- 테스트에서 handler 없이도 도메인 로직이 검증 가능한가?

## 6. Go 테스트 설계와 TDD 관련 세션 정리

### 노트 정리

GopherCon에서는 Go 테스트 설계와 TDD에 대한 강조도 있었다.

- **main 함수 분리**: main 함수의 로직을 run 함수로 분리하고, 테스트에서는 run을 직접 호출하거나 TestMain에서 서버를 한 번만 기동하는 방식이 소개되었다. 이를 통해 테스트 코드에서 별도의 setup 없이 실제 HTTP 요청 기반 테스트를 작성할 수 있다.

- **t.Parallel**: 순수 로직 테스트에서는 적극 권장되며, 동시성 안전성을 조기에 검증하는 데 도움이 된다. 단, DB나 외부 리소스를 사용하는 테스트에는 주의가 필요하다.

- **TDD**: AI 기반 개발 환경에서도 여전히 중요하며, 테스트는 "무엇이 완료 상태인지"와 "무엇이 변하면 안 되는지"를 명확히 정의하는 역할을 한다.

### Reference

main을 run으로 분리하는 패턴은 Mat Ryer, Dave Cheney 등 Go 커뮤니티에서 반복적으로 공유된 실전 팁이다. 이는 테스트를 "실제 서버처럼" 작성하게 만들어 mock 의존도를 낮춘다.

t.Parallel은 Go 테스트의 핵심 기능이며, 순수 로직 테스트에서 병렬 안전성을 확보하는 데 큰 도움이 된다. 다만 DB, 파일 시스템 같은 공유 리소스가 있는 경우에는 테스트 격리가 선행되어야 한다.

### TIP: Go 테스트 실전 팁

**TIP 1**: 가능한 테스트에는 `t.Parallel`을 기본으로 사용한다.
- 동시성 버그는 테스트에서 먼저 발견하는 것이 가장 싸다.

**TIP 2**: 병렬 테스트에서는 항상 유니크 데이터를 사용한다.
```go
unique := time.Now().UnixNano()
body := fmt.Sprintf(`{"username":"user_%d"}`, unique)
```

**TIP 3**: mock보다 real test를 우선한다.
- TestMain에서 서버를 한 번만 띄우고 실제 HTTP 요청으로 검증한다.

## 7. Go-스러운 추상화 원칙

### 노트 정리

**Small Interface 원칙**은 Go 설계 철학의 핵심이다. 인터페이스가 커질수록 추상화는 약해진다.

- 인터페이스는 설계하는 것이 아니라 발견하는 것이며, 사용하는 쪽에서 정의하는 것이 바람직하다.
- 반환 타입으로는 인터페이스보다 구조체를 사용하고, 입력으로 인터페이스를 받는 패턴이 권장된다.
- Options pattern은 설정 관리와 생성자 설계에서 널리 사용되며, telescoping constructor 문제를 효과적으로 해결한다.

### Reference

Small Interface, Discover interfaces, Accept interfaces return structs는 Rob Pike와 Go 팀이 수년간 강조해온 핵심 원칙이다. 이는 추상을 "미리 설계"하지 말고, 중복과 사용 패턴이 드러났을 때 발견하라는 의미다.

Options pattern 역시 Dave Cheney를 비롯해 많은 Go 라이브러리에서 사실상 표준처럼 사용된다. 생성자가 없는 Go의 특성을 고려한, 가장 Go다운 설정 관리 방식이다.

### TIP: 추상화 관련 내부 규칙 예시

- 인터페이스는 소비자가 정의한다.
- 반환값은 구조체로, 입력은 인터페이스로 받는다.
- 인터페이스에 메서드를 추가할 때는 반드시 테스트 영향 범위를 검토한다.
- 설정 값이 3개를 넘어가면 Options pattern을 고려한다.
