# P-001: Git Clone/Push/Pull Connection Timeout During CI/CD Migration

## Executive Summary
Intermittent git clone/push/pull failures during CI/CD migration with `Connection to stage.collabops.ai closed by remote host` and `fatal: the remote end hung up unexpectedly` errors. 

**Root Cause**: Git streaming transport에 absolute deadline을 적용해 slow/stalled를 구분하지 못하고 정상 clone/push/pull도 끊긴다.

> "Git clone/fetch/push는 지속적인 스트리밍이므로, absolute timeout이 아니라 idle timeout + progress-based liveness가 맞다."

## Root Cause Analysis

### Primary Issue: Incorrect Deadline Semantics
**Location**: `internal/server/tcp_git_server.go:163-164`
```go
_ = tcpConn.SetReadDeadline(time.Now().Add(30 * time.Second))
_ = tcpConn.SetWriteDeadline(time.Now().Add(30 * time.Second))
```

**핵심 문제**: "30초"는 증상이고, **'deadline semantics가 틀렸다'**가 근본이다.

### Deadline Semantics 오류의 결과
1. **Stalled vs Slow 구분 불가**: 느린 전송과 멈춘 전송을 구분하지 못하고 무조건 끊음
2. **TCP 레벨 강제 종료**: Git 프로토콜 흐름(SSH + pkt-line + packfile streaming)보다 상위에서 강제 종료
3. **정상 동작 중 끊김**: CI/CD 병렬로 head-of-line blocking 발생 시 "정상 동작 중"에도 끊김

### Why This Happens Frequently
1. **Long-lived Streaming에 Absolute Deadline 적용**
   - Git operations는 지속적인 데이터 스트리밍
   - Absolute deadline은 request-response 패턴에 적합
   - Streaming에는 idle timeout + progress monitoring이 필요

2. **Timeout Cascade Effect**
   - SSH protocol handler: 5 seconds for request body
   - TCP server: 30 seconds for read/write operations  
   - CI/CD pipeline: Variable, often much longer
   - **단일 Timeout Policy로 통합 필요**

3. **Network Buffer & Resource Contention**
   - Fixed buffer sizes don't adapt to repository size
   - Multiple CI/CD jobs cloning simultaneously
   - Git operations competing for I/O resources

### Push/Pull Specific Failure Modes

Push는 clone보다 failure mode가 더 까다롭다:

1. **원자성(Atomicity) 문제**
   - Timeout으로 연결 끊기면:
     - 클라이언트는 실패로 인식
     - 서버는 일부 refs 업데이트 진행 가능
     - hooks/receive-pack 단계에서 중단 가능

2. **검증 필요 항목**
   - receive-pack 처리 중 connection drop 시 refs 업데이트는 atomic인가?
   - 서버가 partial packfile을 어디에 남기고 정리하는가?
   - hook 실행이 있었다면 재시도 시 중복 실행 문제는?
   - repo lock(packed-refs, ref updates) 경합 시 timeout이 어떻게 작동?

## Long-Term Solutions (근본 치료)

### 1. Correct Timeout Semantics (Idle + Progress + Max)

**핵심**: Absolute timeout → Progress-aware liveness로 전환

```go
type ProgressAwareConnection struct {
    conn                net.Conn
    idleTimeout         time.Duration  // 데이터 흐름 없을 때만 적용
    maxTimeout          time.Duration  // 절대 상한
    progressTracker     *TransferProgressTracker
    lastActivityTime    time.Time
}

type TransferProgressTracker struct {
    bytesTransferred    int64
    lastProgressTime    time.Time
    transferRate        *MovingAverage  // bytes/second
    stallThreshold      time.Duration   // 이 시간 동안 progress 0이면 stall
}
```

**Stall 판정 정의**:
- bytes/sec가 0인 상태가 N초 지속되면 stall
- **예외 처리**: pack-objects 단계처럼 "네트워크 0이 정상인 구간" 고려
- read-side idle timeout과 write-side idle timeout 분리

**동작 원리**:
- Progress가 계속되면 timeout 연장
- Idle timeout: 진짜 아무것도 안 흐를 때만 끊기
- Max timeout: 무한정 잡아먹는 것 방지

### 2. Unified Timeout Policy Across Layers

**현재 문제**: SSH handler 5s / TCP 30s 등 분산된 timeout

**해결**: 계층별 목적이 다른 timeout으로 재정의

```go
type TimeoutPolicy struct {
    HandshakeTimeout   time.Duration  // 짧게 (5s) - 초기 연결 설정
    AuthTimeout        time.Duration  // 짧게 (10s) - 인증 완료
    OperationIdle      time.Duration  // 길게 (60s) - 작업 중 idle 허용
    OperationMax       time.Duration  // 상한 (30min) - 절대 최대
    GlobalConnCap      int            // 동시 연결 제한
}

func (tp *TimeoutPolicy) ApplyToPhase(phase ConnectionPhase, conn net.Conn) {
    switch phase {
    case PhaseHandshake:
        conn.SetDeadline(time.Now().Add(tp.HandshakeTimeout))
    case PhaseAuth:
        conn.SetDeadline(time.Now().Add(tp.AuthTimeout))
    case PhaseOperation:
        // Idle timeout으로 전환, progress monitoring 시작
    }
}
```

**Timeout Layers**:
| Layer | Purpose | Duration | Type |
|-------|---------|----------|------|
| Handshake | 초기 연결 설정 | 5s | Absolute |
| Auth | 인증 완료 | 10s | Absolute |
| Operation Idle | 작업 중 무응답 감지 | 60s | Idle-based |
| Operation Max | 절대 상한 | 30min | Absolute |
| Global Cap | 리소스 보호 | N/A | Connection limit |

### 3. Concurrency Control + Observability

**목적**: 운영 안정화 + 디버깅 가능성 확보

```go
type ConcurrencyController struct {
    maxConcurrentClones   int
    maxConcurrentPushes   int
    perTenantLimit        int
    perIPLimit            int
    queue                 *PriorityQueue
    metrics               *MetricsCollector
}

type MetricsCollector struct {
    operationDuration     prometheus.Histogram
    timeoutEvents         prometheus.Counter
    progressRate          prometheus.Gauge
    concurrentOperations  prometheus.Gauge
    stallDetections       prometheus.Counter
}
```

**핵심 기능**:
- 동시 clone/push 제한
- per-tenant / per-IP rate limit
- Operation별 metrics 수집 (duration, timeout events, progress rate)
- Stall detection 로깅

## Capability Maturity Levels

### L1: No False Timeouts (Progress-based)
**목표**: 정상 동작 중인 연결을 끊지 않음

**구현**:
- Idle timeout으로 전환
- Progress monitoring 추가
- Stall vs Slow 구분

**성공 기준**:
- Timeout-related failure rate < 0.1%
- 정상 progress 중 끊김 0건

### L2: Predictable Behavior Under Load
**목표**: 부하 상황에서도 예측 가능한 동작

**구현**:
- Concurrency limits
- Queueing mechanism
- Per-tenant fairness

**성공 기준**:
- 동시 10개 clone 시에도 모두 성공
- Queue wait time 예측 가능

### L3: Auto-tuning (Optional)
**목표**: 시스템 상태에 따른 자동 조정

**구현**:
- Repository size 기반 timeout 조정
- Network condition 반영
- Historical data 기반 예측

**성공 기준**:
- 수동 개입 없이 다양한 repo size 처리
- 새로운 패턴 자동 적응
