# docs 디렉토리 안내

이 디렉토리는 collabops-git-executor 작업 과정에서 나온 조사 문서, 설계 문서, 정책 문서를 모아 둔 곳이다. 문서가 쌓이면서 지금도 따라야 할 기준과 당시의 기록을 구분하기 어려워졌기 때문에, 아래처럼 세 종류로 나누었다.

```
docs/
├── README.md      # 이 파일
├── _archive/      # 과거 기록: 조사 로그, 완료된 마이그레이션·구현 보고서, 특정 시점의 벤치마크
├── principle/     # 지금도 유효한 원칙·정책·API 계약·운영 가이드 (flat, 하위 디렉토리 없음)
└── design/        # 앞으로 진행할 기능의 설계 문서 (지금은 비어 있음)
```

## 어디에 넣을지

`principle/`은 **기능 설계 문서도, 버그 수정 기록도 아니다.** 이 저장소에 새로 기여하는 사람이 코드를 작성할 때 반드시 지켜야 하는 규칙만 담는다. "이 기능을 왜 이렇게 만들었는가"를 설명하는 문서는 아무리 잘 쓰였어도 principle이 아니다. "코드를 짤 때 무엇을 지켜야 하는가"를 명령형으로 말해야 principle이다.

문서 하나를 놓고 다음 질문을 순서대로 물어보면 된다.

1. 이 문서를 안 읽으면 기여자가 규칙을 어기게 되는가? 아니라면 애초에 principle이 아니다.
2. 특정 기능·마이그레이션·버그를 주어로 삼는가(예: "diff 응답 형식을 이렇게 바꿨다", "TCP timeout 버그를 이렇게 고쳤다")? 그렇다면 규칙이 아니라 기록이므로 `_archive/`에 넣는다.
3. 코드를 어떻게 짜야 하는지를 주어로 삼는가(예: "에러는 이 카탈로그를 거쳐야 한다", "ref 이름은 이 형식만 허용한다")? 그렇다면 `principle/`에 넣는다.
4. 아직 확정되지 않았거나 진행 중인 설계라면 `design/`에 넣는다.

제목에 날짜, "Phase N", "Executive Summary", "migration", "handoff" 같은 표현이 들어가 있다면 거의 항상 `_archive/`다 — 이런 제목은 예외 없이 "그 작업을 했다"는 기록이지 "이렇게 해야 한다"는 규칙이 아니다. API 응답 계약, 코딩 컨벤션, ref 검증 규칙처럼 명령형으로 서술되고 지금도 코드로 강제되는 문서만 `principle/`에 해당한다.

## principle/ 파일명 규칙

원칙 문서는 몇 개 안 되고, 새로 기여하는 사람이 훑어보고 순서대로 읽을 수 있어야 한다. 그래서 하위 디렉토리 없이 flat하게 두고, `00N_주제.md` 형식으로 두 자리 인덱스를 붙인다.

예: `001_go-architecture-guidelines.md`, `004_git-ref-rules.md`

인덱스는 "일반 원칙 → 구체적 규칙" 순서를 따른다: Go/아키텍처 전반의 철학이 앞쪽 번호, 특정 도메인(ref, 로깅, 테스트)의 세부 규칙이 뒤쪽 번호. 문서를 추가/제거할 때 번호가 바뀌면 그 문서를 참조하는 다른 principle 문서의 링크도 같이 고친다.

## _archive/는 원래 구조를 유지한다

`_archive/`는 principle과 달리 원래 `docs/` 밑에 있던 디렉토리 구조(`research/`, `benchmarking/`, `env/`, `performance/` 등)를 그대로 유지한다. 조사 당시의 맥락이 디렉토리 단위로 묶여 있어야, 나중에 찾을 때 더 유용하기 때문이다.

## design/ 사용법

새 기능을 설계할 때는 이 폴더 밑에 문서를 하나 만든다. 설계와 구현이 끝나면 그 문서를 그대로 둘 이유가 없다.

- 앞으로도 계속 참고할 기준으로 남을 문서라면 `principle/`로 옮긴다.
- 구현이 끝났다는 기록일 뿐이라면 `_archive/`로 옮긴다.

즉 `design/`에는 지금 진행 중이거나 아직 결정되지 않은 문서만 남아 있어야 한다.

## 새 문서를 쓸 때

1. 이미 있는 문서와 내용이 겹친다면 새로 쓰지 말고 기존 문서를 고친다.
2. 조사나 디버깅 과정에서 나온 문서는 일단 `_archive/`에 넣는다. 나중에 원칙으로 승격할 가치가 생기면, 그때 `principle/`로 옮긴다.
3. `principle/`에 새 파일을 추가할 때는 위의 `00N_주제.md` 인덱스 규칙을 따른다. 어느 원칙 다음에 읽혀야 자연스러운지 판단해서 번호를 정하고, 뒤 번호를 하나씩 민다.
