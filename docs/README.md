# docs 디렉토리 안내

이 디렉토리는 collabops-git-executor 작업 과정에서 나온 조사 문서, 설계 문서, 정책 문서를 모아 둔 곳이다. 문서가 쌓이면서 지금도 따라야 할 기준과 당시의 기록을 구분하기 어려워졌기 때문에, 아래처럼 세 종류로 나누었다.

```
docs/
├── README.md      # 이 파일
├── _archive/      # 과거 기록: 조사 로그, 완료된 마이그레이션·구현 보고서, 특정 시점의 벤치마크
├── principle/     # 지금도 유효한 원칙·정책·API 계약·운영 가이드 (flat, 하위 디렉토리 없음)
└── design/        # 앞으로 진행할 기능의 설계 문서 (지금은 비어 있음)
```

## 어디에 넣을지

문서 하나를 놓고 다음 질문에 답해 보면 된다.

> 이 문서는 6개월 뒤에도 여전히 정확한 소스오브트루스로 남아 있을까?

- 그렇다면 `principle/`에 넣는다.
- 아니라면, 즉 당시의 조사 결과이거나 완료된 작업의 기록이라면 `_archive/`에 넣는다.
- 아직 만들지 않은, 앞으로 진행할 기능의 설계라면 `design/`에 넣는다.

제목에 날짜, "Phase N", "Executive Summary" 같은 표현이 들어가 있다면 대부분 `_archive/`에 해당한다. 반대로 API 계약, 런타임 정책, 코딩 컨벤션, 운영 가이드처럼 "지금 이 시스템이 어떻게 동작해야 하는가"를 설명하는 문서는 `principle/`에 해당한다.

## principle/이 flat인 이유

원칙 문서는 찾기 쉬워야 하므로, 하위 디렉토리 없이 한곳에 모아 둔다. 원래 `architecture/`, `policy/` 같은 하위 디렉토리에 있던 파일은 어느 도메인에 속했는지 알 수 있도록 `도메인__파일명` 형식으로 이름을 바꾸었다.

예: `architecture/typed-handler-migration-plan.md` → `principle/architecture__typed-handler-migration-plan.md`

밑줄 두 개(`__`) 앞부분이 원래 있던 디렉토리의 이름이다.

## _archive/는 원래 구조를 유지한다

`_archive/`는 principle과 달리 원래 `docs/` 밑에 있던 디렉토리 구조(`research/`, `benchmarking/`, `env/`, `performance/` 등)를 그대로 유지한다. 조사 당시의 맥락이 디렉토리 단위로 묶여 있어야, 나중에 찾을 때 더 유용하기 때문이다.

## design/ 사용법

새 기능을 설계할 때는 이 폴더 밑에 문서를 하나 만든다. 설계와 구현이 끝나면 그 문서를 그대로 둘 이유가 없다.

- 앞으로도 계속 참고할 기준으로 남을 문서라면 `principle/`로 옮긴다.
- 구현이 끝났다는 기록일 뿐이라면 `_archive/`로 옮긴다.

즉 `design/`에는 지금 진행 중이거나 아직 결정되지 않은 문서만 남아 있어야 한다.

## 새 문서를 쓸 때

1. 이미 있는 문서와 내용이 겹친다면 새로 쓰지 말고 기존 문서를 고친다.
2. 조사나 디버깅 과정에서 나온 문서는 일단 `_archive/`에 넣는다. 나중에 원칙으로 승격할 가치가 생기면, 그때 `principle/`로 옮긴다.
3. `principle/`에 새 파일을 추가할 때는 위의 `도메인__파일명` 규칙을 따른다. 최상위(`docs/` 바로 밑)에 있던 파일은 원래 이름 그대로 둔다.
